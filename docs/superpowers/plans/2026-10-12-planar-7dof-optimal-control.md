# Planar 7-DOF Optimal-Control Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a path-following, planar rigid-body/four-wheel-speed vehicle and a minimum-time lap optimizer with throttle, brake, steering, the fitted Hoosier 43075 R20 simplified steady UniTire, fixed 20/80 front/rear drive split, deterministic left/right distribution, and no traction control. After the four-AMK example passes, add an isolated fake single-motor/mechanical-differential test fixture.

**Architecture:** Derive a new, genuinely closed signed XY centerline from endurance telemetry and load that single track artifact in both the existing point-mass solver and the planar optimizer; preserve V11 unchanged as a legacy regression input. Compile a separate `planar-7dof` formulation from the canonical vehicle assembly. Build one set of planar physics equations with NumPy and optimization-facing evaluation, then spatially transcribe the hot lap with a sparse NLP; battery state of charge (SOC) becomes a trajectory state, not an outer fixed-point lap loop. The point-mass solver keeps its own outer SOC coupling loop; the planar model does **not** inherit that structure, and it does **not** reuse the point-mass bisection root-finders, LUT interpolation, or voltage clamps inside the NLP.

**Tech Stack:** Python >=3.12, NumPy >=2.0, unittest (existing project); proposed new optional optimal-control dependency CasADi with IPOPT, subject to the backend gate below.

**Spec:** `docs/project-master-plan.md` §§2, 3.2, 4.2, 6, 8–11, 14.2, 14.5, 15. Solver-state source inspection: `main` at `07739b0` (PR #1, `feature/energy-coupling`, merged 2026-10-13). Supporting design record: `docs/superpowers/specs/2026-10-12-energy-coupling-scope.md`, `.superpowers/sdd/2026-10-12-energy-coupling/{progress,w0-report,w1-report,w4-report,endurance-22-post-w4}.md`, `docs/validation/powertrain.md`. The point-mass worktree is merged; `main` is now the integration branch.

## Global Constraints

- SI units; body +x forward, +y right, +z down (SAE J670); +yaw and +track curvature mean right turns; a positive lateral acceleration points right; wheel order FL, FR, RL, RR.
- Use one new, telemetry-derived, closed prescribed XY path for both models. Preserve the old V11 track unchanged for regression, not as the new shared production map. Do not optimize track width or racing line. Do not infer turn sign from an unsigned radius.
- Seven **mechanical** DOF: longitudinal/lateral/yaw plus four wheel rotations. Position and heading are kinematic pose states; SOC is an electrical state, not an extra mechanical DOF.
- Strict quasi-static loads: no suspension heave/roll/pitch states, damper or inertance force. Simplified steady combined-slip UniTire at zero camber; no tire relaxation states.
- Three controls: throttle, brake, steering; deterministic drivetrain and brake policy; no traction controller, hidden force-clipping controller, or independent wheel-torque optimization controls.
- Positive compression load, tire forces on vehicle, explicit sign validation at every frame boundary (the vehicle frame is now SAE, so the tire lateral/vertical sense matches the MATLAB source and only the longitudinal sense needs checking), immutable parameters, no mutation of caller-owned arrays.
- XML identifies models and parameters; Python implements equations; reuse canonical assembly and named capabilities. Existing point-mass tests and numerical baselines must remain green.
- Comments and XML comments follow repository ASD-STE100 policy; add domain terms to its controlled dictionary when that infrastructure exists.

### Reviewed solver-state baseline (`main` @ `07739b0`) — what PR #1 changed

Read before revising assumptions. Every item is traceable to the cited file or document.

**Structure did not change; only one update rule did.**
- The point-mass energy coupling is **still an outer fixed-point loop** wrapping an SOC-free spatial `solve_lap`. The option that would have removed it (W3, joint speed/SOC fixed point) was **skipped on measured evidence**; W2 (predicted initial SOC profile) was never built; W5 (stint-level seeding) was deferred then dropped. The reconciliation loop and its own hard-coded `trace = 0.5 * (trace + final_trace)` remain (`forward_backward.py:651`).
- The single algorithmic change is **W1**: `solve_lap_with_energy` replaced the fixed relaxation with an undamped update `trace = nxt` plus a divergence guard that reverts to the 0.5 update when `change >= previous_residual` (`forward_backward.py:595-598`, justified by the comment block at `:582-594`). Measured effect: 13 → 2–3 coupling iterations, with identical converged answers.
- **Why that matters here:** Gate A measured the residual ratio at ≈ 0.5002, exactly the hard-coded damping, implying an undamped contraction λ ≈ 0.0004. The coupling map is nearly idempotent, so the iteration count was relaxation waste rather than physics. This *supports* treating SOC as a slow trajectory state in the new model, and it means a **single forward SOC integration is a good seed**. It does **not** validate porting the outer loop into an OCP, and it is not evidence about inside-NLP SOC correctness.

**Validated operating domain (constrains the new model).**
- `motor_mode` now defaults to `"lut"`; the canonical map is 400–600 V (grid 25×129×65, SHA-256 `79a615bb836054818aecc45cd6c7a7d5bdb02967c9dea8d16a0eb26a93559448`, declared in `models/power-plants/amk_dd5_100c.xml`).
- `maximum_bus_voltage = 600 V` is a **regulatory** limit applied as `min(terminal, 600)`; the physical pack OCV reaches 608.688 V at SOC 1.0, so the shipped battery starts at `initial_bus_voltage = 600 V`, compiling to SOC `0.9617234998917527`. `compile_battery_pack` now requires exactly one of `initial_state_of_charge` or `initial_bus_voltage`.
- Extending the axis 530 → 400 V **coarsened** the grid from 2.92 to **8.33 V/point**. In-band LUT-vs-exact agreement is p95 3.0 W / max 135 W (400–530 V band) with a 0.176 N·m low-speed envelope error. Sub-0.1 SOC is deliberately outside the map and uses exact fallback.
- The measured 22-lap stint stayed within **516.95–600.0 V** and ended at SOC 0.2842 — i.e. even the extended floor covers the *stint-reachable* range, not all physics.
- Known hazard to avoid inheriting: out-of-domain LUT queries previously clamped to the map floor and **over-reported available force** (`docs/validation/powertrain.md` records LUT 2070.4 N versus analytical 0.0 N at SOC 0.30 / 34 m/s). The 400 V extension fixes it inside the new domain, but the clamping mechanism is the danger. The planar model must treat the valid domain as a **constraint**, not as something to clamp into.

**Energy-path cost and dual evaluation.**
- Routing the energy path through the LUT was **dropped**, not implemented: measured f_energy was only 0.1–0.4 % of wall time, so `_energy_trace` still calls the exact analytical oracle. Consequences: two motor evaluators coexist (see new gate 7), and the "5.66×" is a *speed-iteration* result, not an energy-model improvement.
- `_energy_trace` derives **one** motor speed for all four motors from vehicle speed and a single `effective_radius`, then scales one operating point by `unit_count`. It therefore cannot represent per-wheel speeds or a left/right split. This independently confirms the plan's existing rule against reusing it for the planar residual.
- On the assembled path, SOC affects the **drive** limit and the steady corner cap but **not** the braking limit (`_available_brake_force` takes no storage state). The point-mass baseline is consequently SOC-independent under braking. Starting the planar model friction-only/zero-regen is consistent with that baseline; a future regen path will not have one.

**Semantics traps in the existing energy reporting (do not compare unlike quantities).**
- `EnergyReport.bus_voltage` is the **open-circuit** pack voltage at the segment-start SOC, whereas `LapResult`/`DriveLimit` voltage is an iterated **loaded terminal** voltage clamped to 600 V. Comparing them silently compares different physical quantities.
- `recovered_energy` is computed as `ΔSOC × pack_capacity_joules` (a charge basis), and a regenerative segment's reported `bus_power` is overwritten with the pack-**accepted** charge power. So `bus_power` cannot be integrated to reproduce `net_energy`; `net_energy` is `consumed − recovered`. The plan's requirement to report terminal bus energy and battery chemical/OCV energy separately is therefore not optional bookkeeping.
- `_build_result` never checks `EquilibriumState.is_feasible`: it records `force_balance_residual`, `yaw_moment_residual`, `combined_utilization` and the active-constraint labels, and nothing more. A `converged` point-mass lap can still contain infeasible segment states, and `converged` means only that the forward+backward profile map stopped moving — not feasibility, not optimality, not root accuracy.
- `EnergyReport.maximum_state_change` means a fixed-point residual in the coupled path but an SOC excursion magnitude under `profile_reused=True`. Any consumer thresholding it must branch on `profile_reused`.
- `LapResult.motor_forward_queries` / `motor_inverse_queries` / `motor_fallback_queries` come from **process-global** LUT counters that are never reset per solve, so they are cumulative and not thread-safe. The plan's domain/fallback observability must difference snapshots around the region of interest, as `DiagnosticsCollector` does.
- Scope note for the Spec line above: `formulations/point_mass.py` and `results/traces.py` are **byte-identical** between `de033b9` and `07739b0`. The earlier physics/dataclass review still holds; what changed is the solver's coupling update, the battery/powertrain interfaces, and the LUT artifact.
- Small robustness gaps worth fixing or not inheriting: `solve_lap_with_energy` lacks the `math.isfinite(tolerance)` check that `solve_lap` has, so a NaN tolerance silently never converges; `DiagnosticsCollector(output_path=...)` opens in `"w"` mode and never closes its handle; and a vehicle without storage reports `minimum_voltage = NaN` with a `RuntimeWarning`.

### Proposed shared-track closure algorithm (to validate before production use)

1. **Choose a common physical seam:** derive candidate start/finish crossings from `laptrig` and XY nearest-return points, then verify same travel direction and locate a short overlap on each side of that crossing (including adjacent recorded lap portions if quality permits). Reject a nearest-position match with opposite heading or a different branch of a self-intersection. Record the source time window, candidate crossing, and any ambiguity.
2. **Integrate velocity without losing units:** use measured `xtime.Time`/`VEast.Value`/`VNorth.Value` at actual timestamps, de-duplicate sample times and reject gaps/outliers. Integrate by trapezoidal quadrature into `x=East`, `y=North`. Treat a constant XY offset and absolute rotation as irrelevant; do not use lateral accelerometer sign to construct geometry. Compare raw, carefully filtered and leave-one-filter-out variants to measure sign/seam stability. Do not clone the legacy circle-fit's causal filter blindly because it can shift geometry.
3. **Register overlapping traversals:** align the early/late overlap using a rigid 2D rotation/translation based on position *and tangent*, excluding low-speed points. Use robust weights to downweight bad GPS velocity samples. Choose a crossing based on measured geometry; if no overlap is trustworthy, use the single lap with an explicitly reported endpoint position/tangent residual rather than inventing a second path.
4. **Fit a closed periodic centerline:** fit a periodic cubic-or-higher spline `r(s)=(x(s),y(s))` to ordered integrated XY samples with arc-length reparameterization. Optimize observation residual plus a curvature-variation regularizer while enforcing exact positional and first/second derivative continuity at `s=0,L`; tune weights against held-out measured points and overlap residuals. The fitted seam may blend locally, but permit a spatially distributed drift correction if supported by observed GPS drift; bound displacement/curvature changes relative to measured noise, prevent sharp seam spikes and self-intersections. Do **not** deform the old V11 radii or set the new lap length to V11's value.
5. **Derive outputs from one geometry:** resample at monotonically increasing arc length; compute heading `atan2(y',x')` unwrapped through the seam and signed curvature `kappa=(x' y''-y' x'')/(x'^2+y'^2)^(3/2)`. Store XY, heading, signed curvature and distance in a new XML-referenced CSV. For point mass, derive `radius_magnitude=1/max(abs(kappa), epsilon_curvature)` using an explicitly validated straight-line ceiling; for the planar model consume signed `kappa` directly. Signed radius is `1/kappa` only where curvature is nonzero; do not serialize infinite radii or make a zero-curvature straight become a tiny artificial turn in the dynamic formulation.
6. **Release gate:** exact spline closure within declared numerical tolerance; seam heading/curvature agreement, curvature integral near `2*pi*winding_number`, no duplicate interior points/nonpositive steps or unintended crossings, bounded overlap/held-out position and tangent residuals, bounded correction and curvature spikes, stability under time-window/filter/mesh changes. Run both models on the **same** loaded new track object, and independently check point-mass start-index invariance and planar hot-lap periodicity. Publish raw-vs-closed overlays and metrics in the validation report. If fit-quality gates fail, keep V11's old point-mass path supported and defer the shared new-track example rather than concealing drift.

## Interfaces and equations to agree on

- `PlanarState = (s, n, e_psi, v_x, v_y, r, omega_fl, omega_fr, omega_rl, omega_rr, soc)` for a **time-domain diagnostic**; spatial NLP omits `s` as a state because it is the independent variable. Elapsed time `t(s)` is an additional quadrature state. State dimension is thus 11 in time including s/SOC (plus clock), not “11 mechanical DOF”. Wrap periodic states `n,e_psi,v_x,v_y,r,omega[4]`; SOC and clock are *not* periodic for a finite one-lap discharge.
- Controls `PlanarControls(throttle, brake, steering)` in [0,1], [0,1], and steering road-wheel angle (rad), respectively; no optimizer wheel-torque variables. Agree steering angle/rate limits from the actual vehicle before example claims.
- `s_dot = (v_x cos(e_psi) - v_y sin(e_psi))/(1-kappa(s)*n)`; `n_dot = v_x sin(e_psi)+v_y cos(e_psi)`; `e_psi_dot = r-kappa(s)*s_dot`. Spatial derivatives divide by `s_dot`; constrain `s_dot >= v_progress_min > 0`, `1-kappa*n > 0`. This excludes standing starts.
- Wheel contact velocities in body coordinates at position `(x_i,y_i)`: `(v_x-r*y_i, v_y+r*x_i)`; rotate front velocity into steer axes. Determine the chosen MATLAB-compatible slip-ratio definition and the evaluated per-wheel `Re(Fz)` from the source before coding: `unitire_simple_solve.m` consumes slip ratio and hub speed rather than calculating them. Match the SAE slip-angle sign with left/right tests. Keep the original hard guards in the NumPy reference; use measured-error smooth replacements only in the symbolic backend.
- Body force equations `m*(dv_x/dt-r*v_y)=sum(F_x_body)-drag`, `m*(dv_y/dt+r*v_x)=sum(F_y_body)`, `I_zz*dr/dt=sum(x_i*F_y_body-y_i*F_x_body+M_z_i)` with front tire-force rotation into body axes. Wheel equations `J_i*domega_i/dt = T_drive_i-T_brake_i-R_eff*F_x_tire_i-M_roll_i`, with sign tests for rolling resistance and braking; this first model needs sourced `I_zz`, wheel inertias, steering range and brake torque capacities added to the vehicle assembly.
- Quasi-static loads `F_z` resolve total `m*g+downforce`, longitudinal `m*a_x*h/wheelbase`, lateral `m*a_y*h/track_width` using existing front-mass fraction, aero balance and lateral-load-transfer distribution. The transfer must use the **signed** `a_y` so that a positive (right-turn) value moves load to the left wheels, matching the point-mass `lateral_transfer_loads` helper. Implicit dependence of loads on accelerations needs explicit algebraic residuals (or a documented converged local solve); forbid negative load and do not silently clip in physics.
- Fixed-split motoring target: `T_fl=T_fr=0.10*T_total`, `T_rl=T_rr=0.40*T_total`. Let per-wheel admissible positive torque be limited by motor speed/voltage/power, with common SOC/bus-power constraints. Combined-slip tire feasibility is enforced in the vehicle/OCP residual; it is **not** an allocator input or a controller-imposed torque cut. Feasible total torque obeys `T_total <= min(T_fl,max/0.10, T_fr,max/0.10, T_rl,max/0.40, T_rr,max/0.40, pack/bus equivalent)`; rear binding therefore caps front at 20/80 rather than reallocating. NOTE: tire slip forces come from UniTire and wheel dynamics; no traction control, no traction-limit-based torque clipping. Tire limit is an optimizer **feasibility constraint**, not a live controller cap. Zero negative drive torque in this first version; friction brakes use fixed front bias 0.65. Do not confuse motor-shaft with wheel torque or four motors with a single motor.
- Motor and battery: sum **four individual** inverter bus powers at their individual wheel speeds and requested shaft torques, and enforce total pack current/terminal-voltage sag **as an algebraic system, not as a clamp plus root-find**: carry pack current `I` and terminal voltage `V` as NLP variables and impose `V = OCV(SOC) - I*R(SOC)`, `P_bus = V*I` and `dSOC/dt = -I/(3600*C_pack_Ah)` together with the cell/current/voltage limits as **inequalities**. This replaces `energy_storage.solve_current`'s clamp-and-discriminant formulation and `assembly.maximum_drive_force`'s fixed-0.5 voltage iteration, neither of which is differentiable. Do not reuse the point-mass `_energy_trace` scalar `wheel_force` conversion. Energy is `integral(P_bus dt)`; `shaft_power=sum(T_motor_i*omega_motor_i)`, with independent reports of terminal bus energy and battery chemical/OCV energy. Pack constraints hold at each transcription stage, not only after solve.
- Voltage domain and initial condition: constrain motor/inverter bus voltage to the validated **[400, 600] V** map domain as an explicit constraint, with an explicitly reported policy (not a silent clamp) outside it; treat 600 V as a hard regulatory ceiling and model the physical pack terminal separately from the clamped motor/inverter voltage. For a like-for-like comparison with the point-mass endurance case, initialize at the no-load regulation voltage (600 V → SOC `0.9617234998917527`) using the `initial_bus_voltage` convention, or state an explicit `initial_state_of_charge`; never both.
- Seed, not port: build the planar seed from a **public** `solve_lap_with_energy` run (now 2–3 coupling iterations) or from `solve_lap` plus one forward SOC integration. Do not reimplement the point-mass outer coupling loop or reconciliation loop in the new model, and do not depend on the private `_storage_trace` / `_energy_trace` helpers.
