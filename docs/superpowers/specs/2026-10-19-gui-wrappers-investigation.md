# GUI Wrappers for Tracks, Vehicle Models and Animation: Investigation

Date: 2026-10-19. Status: findings only. No code and no plan exists yet.

**Request:** "Investigate and plan a similar PyQt6 GUI wrapper to the solver GUI for track generation, vehicle model generation/modification, and vehicle animation exporter. These shall be three separate programs for three purposes, not made into one."

This note records what the investigation found. The three implementation plans will cite it as their spec. Every statement was checked against the checkout at commit `1e6d510` on `main`, with a clean working tree, unless it says otherwise. Throwaway prototypes lived in `/tmp/proto`. Nothing in the repository was changed.

## 1. The pattern to copy: `tools/sim_gui/`

- **Split.** A Qt-free core sits in `tools/sim_gui/`. A thin PyQt6 layer sits in `tools/sim_gui/qt/`. Only `qt/`, `app.py` and `tests/test_sim_gui_qt.py` import PyQt6.
- **Optional dependency.** `pyproject.toml` has `gui = ["PyQt6>=6.5"]`. Qt tests set `QT_QPA_PLATFORM=offscreen`. They create a module-level `QApplication` and skip when PyQt6 is missing.
- **Entry point.** `app.main(argv)` builds the `QApplication` and `MainWindow`. It opens an optional first argument. It honours `SIM_GUI_QUIT_AFTER_MS`. As a script it adds `src` and the repository root to `sys.path`.
- **Window.** A left `QDockWidget`, a central `QTabWidget`, toolbar actions, and `QSettings("Simplified-Vehicle-Models", "sim-gui")`. `closeEvent` confirms before it stops running work.
- **Settings.** A frozen dataclass `RunSettings` with `to_json`, `from_json` and `runner_argv`. Validation reuses the real argparse parser. It redirects stderr and catches `SystemExit`.
- **Work.** `ValidationWorker(QObject)` runs on a `QThread` with a mutex-guarded `cancel()`. `CaseQueue(QObject)` runs a pool of `QProcess` children with a timeout timer.
- **Child environment.** `child_environment()` sets `PYTHONPATH=<root>/src:<root>` and `MPLCONFIGDIR`. It lives in `tools/sim_gui/__init__.py` together with `REPOSITORY_ROOT`.
- **File safety.** `_atomic_json` writes a `.tmp` file and then calls `os.replace`. JSON uses `indent=2, sort_keys=True, allow_nan=False`.
- **Reusable core pieces.**
  - `catalogue.py`: `scan_catalogue`, `read_entry`, `fits`, `candidates`, `tracks`. `scan_catalogue` skips `models/sweeps/`. `tracks()` offers only `closed-xy-profile` tracks, so a new open track will not show in the sim GUI's track list. That filter is deliberate, because the forward runner treats an open track as a standing start. Do not change it silently.
  - `vehicle.py`: `VehicleConfiguration.open`, `.slots()`, `.with_choice`, `.changed_from`, `.parameters(key)`. It is read-only for parameters.
  - `variant.py`: `write_variant`. It stamps every output with "Generated by tools/sim_gui ... Do not edit".
- **Tests.** Run with `MPLCONFIGDIR=/tmp/mplcfg PYTHONPATH=src:. QT_QPA_PLATFORM=offscreen python3 -m unittest tests.<module> -v`. `tests/` has no `__init__.py`.
- **Plan format.** `docs/superpowers/plans/2026-10-18-simulation-gui.md`: header, Global Constraints, Branch Dependency, Fixed Decisions, Output Layout, File Map, numbered tasks with test-first steps, Out of Scope.
- **Repo conventions.** Dev docs go in `docs/dev/` and need a row in `docs/dev/tools-layout.md`. `runs/`, `videos/` and `models/sweeps/` are git-ignored.

## 3. Baseline test failures

**Full suite.** `main` at `1e6d510`, fresh `git clone`, `unittest discover -s tests`: 1,619 tests, 20 failures, 16 errors, 4 skipped (36 failing). Adding the GUI code and the two tool changes (139 new tests; the docs tests of the plans came after this run) gives 1,758 tests with the **same** 36 failures (the failing sets are identical). So the GUI code causes no regression.

The 36 failures come from two causes:
- The `corner_toe_angles` import error below. It breaks `test_animation_cli.RenderTest` (3), `test_run_record_runner.RealRecordRunTest` (1), `test_animation_panels.RecordedRunTest` (1) and `test_run_record_channels.VerticalChannelTest` (2).
- Git-ignored trace files under `docs/validation/iem24-murphy/14dof_simple_trials/` are not in a fresh clone. They break `test_vertical_14dof_evidence` (14 failures, 7 errors) and `test_vertical_between_step` (2 failures, 6 errors).

**First, narrower run.** Tests run before any change: `test_sim_gui_core`, `test_sim_gui_qt`, `test_animation_cli`, `test_tracks`, `test_fsae_dynamic_tracks`. Result: 116 tests, 44 s, 3 failures. All three are in `tests.test_animation_cli.RenderTest`:

- `test_missing_ffmpeg_exits_with_a_message_that_names_it`
- `test_png_sequence_of_a_real_excerpt`
- `test_real_record_renders_to_120_fps_h264`

**Cause (confirmed).** Each test calls `real_child("14dof-simple", "--record")`. That child exits 2 with:

```
ImportError: cannot import name 'corner_toe_angles' from 'simplified_vehicle_models.suspension.corner'
```

`src/simplified_vehicle_models/results/plant_channels.py:243` imports `corner_toe_angles`. `suspension/corner.py` does not define it. The kinematics module has `toe(self, jounce)` at `suspension/kinematics.py:159`. A recent refactor commit, `e76234a` "Split the vertical suspension into kinematics and a force network", touched both files. I did not confirm that this commit removed the function.

**Impact.**
- The failure belongs to the checkout, not to this task. The GUI plans must not fix it, and must list the failures above as known baseline failures.
- `real_child("planar-7dof", "--record")` works. It exits 0 in about 2 s, status `Duration_Limit`, and writes `run_record.npz`. That record names `models/tracks/2024_michigan_endurance_multilap_closed.xml`.
- The 14DoF runner is broken only when the record path runs. Any GUI test that needs a real record must use `planar-7dof`.

## 4. Track generation

### Existing code

- **Loader.** `load_track(path)` in `src/simplified_vehicle_models/tracks/profile.py`. Subtypes: `closed-xy-profile`, `open-xy-profile`, legacy `distance-radius-profile`. It validates that heading is the integral of curvature and that each position step matches its distance step. It reports bad rows by line number. The result has `distance, segment_length, radius, curvature, is_closed, title, path_coordinates`.
- **Open courses.** `tools/tracks/open_course.py` needs only NumPy.
  - Builders: `straight`, `arc`, `arc_by_angle`, `transition`. Each validates its input and raises `ValueError`.
  - `build_course(sections, maximum_spacing=0.25, start_heading=0.0, start_north=0.0, start_east=0.0, allow_curvature_jumps=False, jump_ramp_length=0.05)` returns an `OpenCourse`. Without `allow_curvature_jumps` it raises `ValueError`. The message gives the jump size, the distance and both section names.
  - Writers: `csv_text`, `xml_text`, and `write_course(course, directory, stem, model_id, title, comments, parameters, source) -> (xml_path, csv_path)`.
- **Presets.** `tools/tracks/build_fsae_dynamic_tracks.py` has `acceleration_course()` and `skidpad_course(transition_length)`. Constants: `SKIDPAD_CIRCLE_RADIUS`, `SKIDPAD_ENTRY_LENGTH`, `SKIDPAD_EXIT_LENGTH`, `SKIDPAD_NODE_SPACING=0.25`, `SKIDPAD_JUMP_RAMP_LENGTH=0.05`, `ACCELERATION_LENGTH=75`, `ACCELERATION_STAGING_OFFSET=0.30`, `ACCELERATION_NODE_SPACING=0.30`.
- **Closed tracks.** `tools/tracks/build_closed_track.py` needs SciPy.
  - `build_geometry(telemetry, start, end, spacing, smoothing)` returns a dict. Keys include `distance, north, east, heading, curvature, length, winding, closure_gap, minimum_radius, minimum_self_distance, peak_smoothing_correction`.
  - `write_csv(path, geometry)` and `write_xml(path, csv_name, geometry, telemetry, maximum_radius, spacing, smoothing)`.
  - `report(geometry)` prints to stdout.
  - `tests/test_closed_track.py` imports from this module, so its signatures must stay stable.

### Verified

- A section list of `SectionSpec -> Section` reproduces both committed FSAE builders **exactly** (same node count, positions, curvature and section names): the acceleration course, and the skidpad with `transition_length` 0.0 and 6.0.
- `write_course` followed by `load_track` round-trips an open course (`is_closed` False, length correct).
- A synthetic MAT file works with `build_geometry` / `write_csv` / `write_xml` and then `load_track`. Layout: `savemat(path, {"xtime": {"Value": t}, "VNorth": {"Value": ...}, "VEast": {"Value": ...}})`. A 30 m circle gave length 187.7 m, minimum radius 29.8 m and closure gap 0.0. Both rotation directions load as closed. So closed-mode tests need no real telemetry.
- The runner treats an open track as a standing start (`track_is_closed` false in the summary).

### Problems found

1. **`xml_text` does not escape its input.** An id containing `"`, a title containing `&` or `<`, or a comment containing `--` produces malformed XML. The test case `id='a"b'`, `title='Tom & Jerry <1>'`, `comment='bad -- comment'` raised `ParseError`. The GUI must validate these fields before it writes. Fixing `open_course.py` is optional and would not change the committed tracks.
2. **`write_xml` is tied to one event.** It hard-codes `MODEL_ID = "2024-michigan-endurance-closed"`, the title "2024 Michigan Endurance Closed", and `SOURCE_MAT` is a Desktop path. The CLI cannot set the id or title. Options: add keyword-only `model_id=` and `title=` parameters with the old values as defaults (the default behaviour stays byte-identical), or rewrite those two fields in the written file.
3. **The two FSAE track XMLs are generated.** `fsae_2026_skidpad.xml` and `fsae_2026_acceleration.xml` say "Generated by tools/tracks/build_fsae_dynamic_tracks.py". `test_fsae_dynamic_tracks` checks that the committed files match the generator. The track GUI must not overwrite them without an explicit confirmation.
4. `closed-xy-profile` is the only subtype the sim GUI will offer. A GUI-built open track is valid input to `load_track` and to the animation exporter, but not to the sim GUI track list.

### Design implications

- **Mode A (primary): open-course section editor.** A section table, a live XY preview, a curvature-versus-distance plot, jump warnings from `build_course`, spacing and start pose, and presets (acceleration, skidpad, skidpad with clothoids). It saves through `write_course` and validates by reading the file back with `load_track`.
- **Mode B: closed track from MAT telemetry.** A lap window, spacing, smoothing, maximum radius and the `report()` figures. It is optional because it needs SciPy.
- **Plotting.** Two options: custom `QPainter` widgets (no dependency, and `.venv` stays usable) or matplotlib `FigureCanvasQTAgg` (richer, works under system `python3` only). Open question.

## 5. Vehicle model generation and modification

### Model structure

- Files are XML: `<model schema-version id type subtype>`, then `<parameters><parameter name value unit/>`, `<components><component role ref/>`, `<data ref|path ...>`, `<source ref>` (formulations), `<metadata>`.
- Tags that carry `ref` or `path`: `component`, `data`, `source` only.
- 62 XML files under `models/`, 342 parameters. Every `<parameter>`, `<component>`, `<source>`, `<data>` and root `<model>` tag is on one line. None uses single-quoted attributes.
- Validation lives in `xml/schema.py` and `xml/loader.py`. Components use a closed parameter list (unknown, missing or wrong-unit parameters raise `ValueError`). Assemblies allow extra parameters and record them as unconsumed.
- `compile_formulation(path)` takes about 0.02 s and returns `CompiledFormulation(model, manifest)`. `manifest` has `loaded_components`, `unused_components`, `unconsumed_parameters` (`name, unit, value`), `capability(name)`, `component(role)`, `unused_roles()`. The planar 7DoF formulation reports 5 unconsumed parameters (for example `pitch_radius_of_gyration`) and unused roles `('suspension', 'tire-transient')`. The 14DoF formulation reports none. A GUI can show which edits have no effect on the chosen model.
- Slots of the planar 7DoF configuration: `tire, aero, powertrain, powertrain/power-plant, powertrain/energy-storage, drivetrain, drivetrain/transmission, drivetrain/controller, suspension, suspension/kinematics, suspension/spring, suspension/arb, suspension/damper-front, suspension/damper-rear, tire-transient`.

### The sim GUI is read-only for parameters

`VehicleConfiguration.parameters` only reads. This is a documented design rule of the sim GUI ("The GUI never changes a parameter"). The vehicle GUI fills that gap and must not change the sim GUI's behaviour.

### Protected files

- **Seven** files carry a "Do not edit" comment from a generator: `anti-roll-bars/iem24_murphy_real_suspension_arb.xml`, `dampers/multimatic_dssv_vc01_front.xml`, `dampers/multimatic_dssv_vc01_rear.xml`, `hydraulics/iem24_roll_decoupled_circuit.xml`, `springs/iem24_murphy_real_suspension_springs.xml`, `suspension-kinematics/iem24_murphy_real_suspension_kinematics.xml`, `suspensions/iem24_murphy_real_suspension.xml`. The generators are `tools/model_data/generate_suspension_lut.py`, `generate_damper_lut.py` and `generate_hydraulic_circuit.py`.
- Two more are generated tracks (section 4, item 3). Total: 9 generated files.
- Many tests pin SHA-256 hashes of `models/` files (`test_component_sweep`, `test_forward_driver_runner`, `test_powertrain`, `test_suspension_corner` and others). Any in-place edit of a baseline file can break them. The default must be save-as-new outside `models/`, with an explicit confirmation to write into `models/`.
- A run record hashes the files it used, so edited copies keep their own ids.

### Saving XML without losing information

- `ElementTree.parse` drops all comments (0 of 7 kept in `iem24_murphy_real_planar.xml`). With `XMLParser(target=TreeBuilder(insert_comments=True))` 6 of 7 stay. Comments before the root are still lost.
- `ElementTree` round trip changes the bytes of **35 of 62** files, mostly `<x />` becoming `<x/>` (or the reverse). Only 27 are byte-identical.
- A text-level editor avoids this. Prototype: edit only the `value="..."` of `<parameter>`, the root `id`, and `ref` / `path` on `component`, `data` and `source` tags, and leave comments untouched by splitting on `<!-- ... -->`. Results on all 62 files:
  - identity (no edit, same directory): byte-identical 62 of 62
  - re-anchoring references into the same directory: byte-identical 62 of 62
  - a parameter edit changes exactly the intended lines (`id` and `total_mass` in the test)
  - a comment containing `<parameter name="x" value="1"/>` is not edited
  - edited copies load with `load_model` and compile with `compile_formulation`
- **Save pipeline prototype** (edit parameters at several slots, including a nested one, then write copies and the formulation): it produced `__formulation.xml`, `__vehicle.xml`, `__tire.xml`, `__powertrain.xml` and `__powertrain__power-plant.xml`. All references re-anchored. The result compiled (ids with the `.mytest` suffix). Reopening it showed the edited value (`cg_height` 0.315 against 0.300). The baseline files were unchanged. The existing `write_variant` already does the same for slot swaps, so the editor can reuse its approach: copy each nesting component on the path to a changed slot, deepest first.
- Floating-point edits written with `repr(float(x))` round-trip exactly.

### Other notes

- `tools/model_data/generate_component_sweep.py::generate_sweep(base, target, operation, numbers, output, *, name, unit=None, force=False, command=None)` is the route for NPZ / LUT data edits. It needs a leaf component and allows 1 to 100 numbers. NPZ data uses `allow_pickle=False` and only float arrays can be swept.
- `tools/data/import_vehicle_spec_sheet.py` imports an XLSX spec sheet. It has 7 required `--output-*` flags (vehicle, aero, motor, battery, powertrain, ackermann, pedal-ratio) and many numeric options. It loads `openpyxl` lazily. `tests/test_planar_7dof.py` refers to it. This is an optional last task.
- Vehicle GUI scope proposed: open vehicle or formulation, slot tree, editable parameter table with unit and finite-value checks, save-as-new, compile check with unconsumed-parameter report, swap, and clone. Generated files open read-only.

## 6. Animation exporter

### Existing code

- `tools/anim/export_animation.py`: `build_parser()`, `Plan(args)`, `describe(plan)`, `run(plan)`, `main(argv)`.
- Options: `--record --output --png-sequence DIR --frame-rate (120) --width/--height (1920x1080, even) --crf (0-51, 18) --preset medium --time-range T0 T1 --force-top-view --quasi-static-attitude --dry-run --progress`, plus STL and scene options (`--stl-body --stl-wheel --body-length/-width/-height --wheel-radius --wheel-width --transform-scale/-x/-z`).
- Exit codes: 0 success, 2 `CliError`, 3 `EncoderUnavailable`. argparse errors exit 2 through `SystemExit`.
- `Plan` loads the record without matplotlib, checks sources (a mismatch becomes a warning), builds `FrameSource`, and decides window visibility. Building it for a 0.6 s record took 1 ms. `describe(plan)` returns the text of the dry-run: record path, model, rows and time range, frame count and video length, size and layout, estimated output size, channels, visible and hidden windows, and warnings.
- `plan.visibility` is a `WindowVisibility` with `visible`, `hidden`, `notes` over the windows `("gg", "track", "rear", "right", "top")`. `plan.source` has `count`, `warnings`, `scales()`. `plan.record.manifest` has `track`, `coarse_for_120_fps`, `model`, `channel_names`.
- Importing `export_animation` does not import matplotlib. Matplotlib loads in `run()`.
- **Progress** goes to stderr with `--progress`, one line per `progress_interval` of 1 s:
  `frame {done}/{total}  {rate:6.1f} frames/s  eta {remaining:6.0f} s`. Prototype regex: `frame\s+(\d+)/(\d+)\s+([\d.]+|nan)\s+frames/s\s+eta\s+(\d+|nan)\s+s`. It parsed both a normal line and one with `eta nan`. Before the progress lines the CLI prints the `describe` text. The final line is `rendered N frames in X s (...)`.
- **Encoding.** `find_ffmpeg()` raises `EncoderUnavailable` with a message that names ffmpeg. `FfmpegFrameWriter` writes `<name>.partial.mp4`, then `os.replace`. On failure it deletes the partial file. A child killed by the GUI will not run that cleanup, so the GUI must delete `*.partial.mp4` itself on cancel.
- Panel `update(index)` draws from the index alone (for example `trace_points(index)` slices the data). So a single frame can be rendered at any index, which supports a preview or scrubber without playing the sequence in order. This is from reading the code, not from a scrubbing test.

### Measured

- Real planar-7DoF record (73 frames at 120 fps, 320x240, PNG sequence): **41.1 ms per frame**, 3.0 s render, 3.4 s total including start-up. All 73 PNGs were written. The render-to-real ratio was 4.9.
- That record carries a track (`models/tracks/2024_michigan_endurance_multilap_closed.xml`) and `coarse_for_120_fps` is True, which gives a visible warning.
- `--dry-run` works on a synthetic record. A **synthetic record has no track**, so a real render exits 2 with "cannot load the track named by the record: the record names no track file". Tests that render must therefore use a real `planar-7dof` record, or a synthetic record whose manifest names a track. Dry-run tests can use the synthetic `record_file` helpers (`tests/test_animation_cli.py`; `make_source` and the channel lists come from `tests/test_animation_panels.py`).
- `study.json` entries (schema `sim-study-v1`) hold `run_record` as a path relative to the study directory, or `None`. Each case has `id`, `label`, `model`, `track`, `status`, `summary`.

### Design implications

- Pick a `run_record.npz` directly or from a `study.json`. Show the dry-run plan. Edit time range, rate, size (even numbers), CRF, preset, MP4 or PNG sequence, and the display options. Disable MP4 with a message when `find_ffmpeg()` fails.
- Run the export as a `QProcess` child of `export_animation.py --progress`, which keeps the GUI responsive and makes cancel simple. Map exit 2 and 3 to messages. Write under `videos/`, which is git-ignored.
- Preview one frame by running the CLI with `--png-sequence` and a narrow `--time-range`, then show the PNG in a `QLabel`. At about 40 ms per frame plus start-up, this takes a few seconds, so it must run in the background.

## 7. Cross-cutting findings

- **Shared code.** All three programs need `REPOSITORY_ROOT`, `child_environment()`, an atomic file writer and a `QProcess` log runner. Importing `sim_gui` internals from the other programs would couple them. Alternatives: a small `tools/gui_common/` package, or three copies.
- **Layout (proposed).** `tools/track_gui/`, `tools/vehicle_gui/`, `tools/anim_gui/`. Each has `__init__.py`, a Qt-free core, `qt/` and `app.py`. Each runs as `PYTHONPATH=src:. python3 tools/<x>_gui/app.py`. Separate `QSettings` names (`track-gui`, `vehicle-gui`, `anim-gui`) and separate quit-after-ms variables. Each has its own tests (`tests/test_<x>_gui_core.py`, `tests/test_<x>_gui_qt.py`), a doc in `docs/dev/`, and a row in `docs/dev/tools-layout.md`.
- **Files outside the repository.** Track and vehicle outputs default to a user folder, not `models/`. Writing into `models/` needs a confirmation. Every write uses the temp-file-then-`os.replace` pattern.
- **Branch.** The sim GUI is merged (PR #10). The current branch is `main`. Implementation should use a worktree under `.worktrees/` (git-ignored).

## 8. Open decisions

Recommended defaults are first. **Resolved on 2026-10-19:** items 1, 4, 5, 6 and 7 were decided by the user. Items 2 and 3 got no answer, so the plans use the recommended default and state it in their Fixed Decisions.

1. **Decided: QPainter.** **Plotting for track previews:** custom `QPainter` widgets, or matplotlib `FigureCanvasQTAgg`.
2. **Default used (no answer):** **Vehicle editing depth:** parameters plus save-as-new and slot swap first, with LUT / NPZ data only through the generators. Alternative: also create new components and vehicles.
3. **Default used (no answer):** **Edit in place or save-as-new:** save-as-new by default, with an explicit confirmation to write into `models/`.
4. **Decided: no in-app playback.** **Animation preview:** a still-frame preview plus export. Alternative: in-app playback.
5. **Decided: shared package.** **Shared code:** a small `tools/gui_common/` package. Alternative: three independent copies.
6. **Decided: add the arguments.** **`write_xml` and `xml_text`:** add backward-compatible keyword parameters (and optional escaping), or leave both files untouched and work around them in the GUI core.
7. **Decided: one plan per program.** **Plan files:** one plan per program (`2026-10-19-track-gui.md`, `-vehicle-gui.md`, `-animation-gui.md`), as the `writing-plans` skill asks for one subsystem per plan.
